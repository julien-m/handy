## Notes

- **Step 2, deviations from the plan text:**
  - The starter marker is the settings schema version (2 → 3), not a new `prompt_starters_migration_version` field: it is already the persisted migration marker of `apply_settings_migrations`, and a new stored field would have needed a reviewed descriptor row for an internal value. Fresh installs get the starters from the defaults with version 3.
  - UI commands commit through the existing `tauri_adapter::edit` (typed edit on the locked latest settings in the write order) instead of a new `tauri_adapter::write_change`: the UI commands carry no base revision, and the CLI domain (Step 3) runs the same pure `prompts::library` edits, so both surfaces refuse identically.
  - The prompt UI commands moved from `shortcut/mod.rs` to the new `commands/prompts.rs` (same command names, so the frontend calls are unchanged); `set_post_process_selected_prompt` now takes `Option<String>` and refuses a prompt with issues (`prompt_not_usable`).
  - The Apple Intelligence platform capability and the provider override edit (plan Step 3) are delivered here, because the override UI command needs them.
- **AC-001 precision to carry into the spec (orchestrator decision 4):** a prompt text made only of whitespace is refused (`prompt_text_empty`): the text must be non-empty after trimming, 1–8000 characters; the stored text stays verbatim.
- **Step 3, deviations from the plan text (names merged with 004):**
  - Prompt shortcuts are stored in the shared `bindings` map under the action id `prompt:<prompt id>` (004's authoritative representation; a prompt without shortcuts has no entry). There is no separate `PromptShortcutRegistry` adapter: 004 is merged, so 005 calls its conflict check (`plan_shortcut_edit`), registration delta and preparation directly; `shortcut/prompt_targets.rs` holds the prompt-target rules (0–2 shortcuts, no default, `reset` removes them, the last one may be removed).
  - Deleting a prompt removes its target in the same edit. The UI command uses `tauri_adapter::edit_prepared(app, "bindings", …, live_change::bindings(…))` (the plan's `commit_prepared_edit` no longer exists); a routed CLI `prompts delete` goes through the extended `RoutedBackend::commit_change`, which now takes 004's `bindings` preparation through the existing `sequence::write_change_prepared` (a change that does not touch `bindings` skips it, so other domains commit as before). During a dictation both are refused with `unavailable` (`shortcut_session_busy`), typed and translated (orchestrator decision 2).
  - Switching AI post-processing on/off registers/releases the prompt shortcuts with the post-processing ones (004's `post_process_enabled` preparation, extended in `shortcut/gated.rs`); the switch itself is refused during a dictation, so the plan's "switch off during a recording" case cannot happen.
  - `DomainPlan::Change` gained an optional `render`, so `create`/`update`/`set-provider-override` answer with the prompt (and its id), `delete` with the removed shortcuts and `set-default` with the default.
  - `prompts list` reports readiness through `prompts/provider.rs` (delivered here, used by Step 4) and a probe for Apple Intelligence that only runs inside the instance, on a bounded worker, and only when a prompt resolves to it.
  - `ShortcutBinding::shortcuts()` skips an empty first shortcut (a prompt target without shortcuts), never an entry to register.
  - `Dispatch::App` boxes the parsed arguments (clippy `large_enum_variant` once the prompts subcommand was added).
- **Step 3, not proven by an automated process test:** the routed `prompts delete` with shortcuts during a dictation (needs the Tauri runtime and the coordinator lease); the preparation/compensation pieces are unit-tested with a fake backend and the refusal is 004's lease. Native macOS evidence stays a Step 8 item. The keyboard-implementation switch repairs only the default actions' lists (004 `plan_switch_repair`); a prompt shortcut invalid for the destination implementation stays stored and its registration fails (logged).
- **Step 4, deviations from the plan text:**
  - The 30-second budget is one `tokio::time::timeout` around the whole step (Apple availability, structured request, llm_client's retry without reasoning fields, legacy fallback, parsing): dropping the future at expiry cancels the HTTP request, so `llm_client` needs no deadline parameter. Tests use scaled budgets (hundreds of milliseconds, wide margins) instead of a fake clock: tokio's paused clock needs the `test-util` feature, which the crate does not enable.
  - The real-HTTP processing tests are in-crate (`prompts/processing_http_tests.rs`, real loopback server, production `NativeProviders`) rather than `tests/prompt_processing.rs`: the provider types live in the private `settings` module, which integration tests cannot name.
  - A structured reply that is not JSON, or lacks the `transcription` field, is still used as is (clarified `[ASSUMED]` behaviour); an empty or whitespace-only reply once cleaned is now a failure (`empty_result`) instead of being inserted. A default prompt that names a missing prompt fails with `prompt_missing` (raw text kept), and a default of None means no processing.
  - Apple Intelligence keeps one native worker slot; a request while it is held fails at once with `provider_busy`, and a late native result is discarded. Real Apple Silicon evidence stays a Step 8 item.
- **Step 7, as decided by the orchestrator (decision 3):** no `audio_available` column — a row without audio is `file_name` NULL, as delivered by 006 (migration 5, text-only rows, `history_status` from the real save). 005 adds only migration 6: five nullable columns (`post_process_prompt_id`, `post_process_prompt_name`, `post_process_provider_id`, `post_process_model`, `post_process_failure`), exposed flattened in `HistoryEntry` as `ProcessingRecord`. The retry of a history row rewrites the record of its new AI step. The history UI that shows the failure is part of the UI pass.
- **Step 5, deviations and limits:**
  - The session tests (plan `src-tauri/tests/prompt_sessions.rs`) are in-crate (`prompts/session_tests.rs`), on the pure session state, because the settings types are private to the crate. They follow orchestrator decision 2: changing or deleting a prompt's shortcuts during a dictation is refused by 004's lease (a deletion of a prompt with shortcuts changes the shortcut lists and so takes the lease; one without shortcuts does not and never changes a captured prompt), and switching AI off is refused during a session, so the plan's "switch off while recording" race does not exist.
  - The prompt and its provider are captured when chosen (start or indicator choice) from one settings view, then frozen at the stop; a later edit or deletion never changes them. A default naming a missing prompt is recorded as `prompt_missing` with the original text.
  - The failure notice is a typed event (`prompt-processing-failed`, at least 4000 ms, translated key `overlay.fallbackNotice`: "AI processing failed. The original text was used."); it is emitted after the history write and before the insertion and never reports the insertion result. **Showing it on the indicator for 4 seconds independently of the overlay hide, and the indicator menu itself, are UI work (Steps 1 and 6) not done in this run;** the case of the overlay style `none` stays an open, non-critical ambiguity of the review.
  - Not covered by an automated end-to-end test: the real pipeline (microphone, transcription, insertion) with a session; the pieces are unit-tested (session, processor, output decision, history store) and the glue is `prompts/dictation.rs`. Native macOS evidence stays a Step 8 item.
