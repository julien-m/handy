## 2. Démarrage (`3f26053`)

- **Bail et normalisation unique** : conformes. `install_owned` → `initialize` normalise une seule fois sous le verrou de transaction, garde le bail et publie le snapshot. Un store déjà normal n'est pas réécrit. Le plugin single-instance tourne pendant `build()` (`initialize_plugins`) et sort par `std::process::exit(0)` si une instance répond. Le `setup` utilisateur ne tourne qu'au `RuntimeRunEvent::Ready` (tauri `app.rs:1424`). L'hypothèse de `ClaimedSingleInstance` tient donc. Si une autre erreur de socket survient, le plugin lance l'application quand même, et le bail flock protège encore contre une seconde instance récente.
- **« Installé avant tout lecteur »** : faux sous macOS (constat M1).
- **Headless** : conforme. `install_offline` lit sans créer le store (seul `settings.lock` peut être créé si le parent existe, comme documenté), puis écrit en écrivain hors ligne, refusé tant qu'une instance détient le bail ou que le socket existe.
- **Plugin store** : aucun code Rust n'ouvre plus `settings_store.json` (pas de `StoreExt`, pas de `store_path(SETTINGS_STORE_PATH`). Le gestionnaire `RunEvent::Exit` du plugin (`tauri-plugin-store` `lib.rs:448-456`) ne sauvegarde que les stores chargés, donc aucun cache de réglages n'existe à vider. Le plugin reste toutefois enregistré, et les webviews gardent `store:default` (constat m3).
- **Store illisible** : un JSON invalide passe bien en lecture seule (sonde : `recovered=true`, écriture `persistence_failed`, octets inchangés). Un fichier illisible pour d'autres raisons fait échouer le démarrage (constat M2).
- **Concurrence** : correcte entre l'instance graphique et un écrivain hors ligne. L'écrivain relâche le bail avant le verrou de transaction (ordre des champs de `LockedDocument`). `initialize` attend donc le verrou de transaction, puis obtient le bail sans blocage, et voit un commit complet. Un écrivain hors ligne qui commence après le `bind` du socket single-instance est refusé par le probe. Avec un socket périmé, l'instance graphique démarre (le plugin nettoie sur `ConnectionRefused`), mais les écrivains hors ligne restent refusés : limite connue, la récupération prouvée par bail est prévue à l'étape 5.

## 4. Robustesse

- Aucun `unwrap()`, `expect()`, `panic!` ni `unreachable!` ajouté dans le code de production par `61a2d4a` ou `3f26053` (grep des lignes ajoutées). Les verrous `std` utilisent `unwrap_or_else(PoisonError::into_inner)`. Les affectations par index `document.raw[...]` ne portent que sur des documents objets : `check_revision` refuse un document non inscriptible avant.
- Il existe toutefois un panic indirect : une erreur de `setup` devient `panic!("Failed to setup app")` dans tauri (constat M2).
- Deadlock : aucun trouvé. L'ordre des verrous est le Mutex `commits`, puis le verrou fichier de transaction. Les fermetures d'édition sont pures (vérifié pour shortcut, models, audio et model manager) et ne rappellent pas le service. Les effets tournent après le relâchement de `commits`. Les réparations déclenchées par un effet (`persist_tauri_fallback`, `persist_binding_resets`, repli micro) peuvent donc reprendre le Mutex sans réentrance. `refresh()` sur issue inconnue reprend le verrou fichier après le relâchement du `LockedDocument`. En revanche, les effets hors section sérialisée posent un problème d'ordre (constat m1).

### Observation hors périmètre, à porter à l'étape 5

`instance_probe.rs` : sous Linux, `classify_owner(Ok(false), CurrentSession)` renvoie `Uncertain`. Un écrivain hors ligne (`NativeOwnerProbe`) est donc toujours refusé sous Linux, même sans aucune instance. Un run headless ne peut jamais persister une réparation. La future écriture CLI hors ligne d'AC-005 (« When none is running, the CLI applies the operation itself ») serait impossible sous Linux. C'est conforme au tableau du plan (« unknown scope refuse mutation »), mais en tension avec AC-005 : à trancher avant l'étape 5.
