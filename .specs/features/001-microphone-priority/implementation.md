## Follow-ups (delivery review warnings, documented only)

- **Needless always-on reopens (performance, accepted after round 2):** with a present first choice that cannot be opened (busy, broken driver, Bluetooth profile switch), every always-on recording start closes the healthy fallback, retries the failing choice (up to 2 s) and reopens the fallback before capture, because the presence-only check still prefers the failing choice. This is the price of AC-004 (a reconnected higher choice always wins at the next start). A safe optimization must skip only the choices that failed, never what is ranked after them, and keep the stream only when the first present choice that did not fail is the open one; it needs its own tests on the manager seam. To measure with the Step 7 latency samples.
- **Priority list size cap:** no count cap on `microphone_priority` (plan decision); the 008 request size bounds it. If a cap is wanted (for example 32 entries with `limit_exceeded`), it needs a spec decision and a contract update of `set-priority` first.

- **System default outside the attempt budget (pre-existing):** for the system-default attempt, `host.default_input_device()` and then the name read of the opened device (`device_name()`) run on the caller thread, outside the 2 s handshake. CoreAudio can block on them, so the 6 s bound does not cover that slot. The behavior is the same as before 001. Follow-up: resolve the default and read the name inside the attempt worker, and return the name in the handshake.
- **Failed reopen invisible after a priority change:** the `microphone_priority` live effect queues a worker and the commit reports success. If the always-on reopen then fails, the failure is only logged, the stream stays closed and nothing tells the user before the next recording start, which resolves again. Follow-up: surface it (a status warning in `get_microphone_status`, or an event), or document the asynchronous acceptance in the contract.
- **Transient cpal error on Linux ALSA:** every cpal error callback sets the stream's error flag, and the consumer reports a loss that ends the recording. On ALSA, cpal 0.16 also calls the error callback for POLLERR (capture overrun) and non-fatal backend errors, so such an error can cut a dictation short (the prefix is kept). Follow-up: classify `cpal::StreamError` and report a loss only for `DeviceNotAvailable` or when callbacks stop; add this case to the pending Linux release evidence.
- **Start latency:** with a non-empty priority, every always-on recording start checks the preference on a fresh catalog under the state lock: the lid probe (up to 1 s with a clamshell override), then an enumeration (40-110 ms normally, up to 4 s if it hangs). On-demand starts enumerate at every opening. The latency samples planned for Step 7 (macOS) are still to be collected. Short enumeration budget for the always-on check to be considered.
- **Device names in existing logs:** the pre-existing `info` log "Using device: …" (`recorder/opening.rs`, `log_stream_config`) now runs on every resolution, and the `error!` of a failed always-on reopen (`audio_priority.rs`) prints backend messages that may name a device. The new 001 logs (`log_resolution`) carry no device name. Follow-up: drop to `debug` without the name and log failure kinds.
- **Interim "Default" selector (resolved by Step 6):** the single selector and `promotedOrder` are removed; the editor saves the complete order, so a multi-entry order saved by `microphones set-priority` is only changed by explicit edits.

## UI delivery review, correction round 2 (2026-10-14, branch `feature/ui-001-microphones`)

Fixed after the BLOCKED `review` (1 blocking) and the PASS `audit` (1 warning) of round 2. The next round is the last one. Proofs: [proofs/claude-ui-fix2/summary.txt](proofs/claude-ui-fix2/summary.txt).

- **Blocking — polling not paused on Windows:** the window hide (`window.hide()` in `lib.rs`) does not reach WebView2 with wry 0.55.1, so `document.visibilityState` very probably stays `visible` there. The polling now also asks the Tauri window: `window-visibility.ts` answers `getCurrentWindow().isVisible()` (permission `core:window:allow-is-visible`, already granted by `core:default` through `core:window:default`) and subscribes to `onFocusChanged` (`core:event:allow-listen`, also in `core:default`). `status-polling.ts` combines both sources (`allVisible`, the page first): before each read it asks; a hidden answer stops the timer and drops the pending read, so a hidden window costs one `isVisible` call and then nothing; a focus change asks again, and reopening from the tray (`show_main_window` shows and focuses the window) reads at once and restarts the 5 s timer. `visibilitychange` stays as the other signal. ## UI hardening pass (2026-10-14, branch `fix/ui-hardening-a`)

Warnings of the UI delivery review round 3 (`drui001-review-r3`, `drui001-audit-r3`, both PASS). Proofs: [proofs/claude-hardening/summary.txt](proofs/claude-hardening/summary.txt).

- **Polling resume without a focus event:** `show_main_window` (`src-tauri/src/lib.rs`) emits `main-window-shown` (`MAIN_WINDOW_SHOWN_EVENT`) after unminimize, show and focus, from every entry point (tray, dock, second launch, `show_main_window_command`). `window-visibility.ts` subscribes to it through `listen` (`core:event:allow-listen`) in addition to `onFocusChanged`, so a reopened window whose `set_focus` is refused (Windows foreground lock, Wayland) still reads at once and restarts the 5 s timer. `window-visibility.test.ts` checks that the frontend name matches the Rust constant and its `emit`.
- **Minimized window:** `isOnScreen` asks `isVisible()` then, for a shown window only, `isMinimized()` (`plugin:window|is_minimized`, in `core:window:default`, so in `core:default`). A minimized window counts as hidden on every platform; on Windows this covers `IsWindowVisible` staying true and WebView2 not being told. Pausing happens at the next period at the latest (or at once on the blur that usually comes with a minimize); a restore resumes on the focus event or `main-window-shown`. A failure of either call keeps the documented fallback (visible, logged once).
- **Conflict banner:** `canSave` (`draft-state.ts`) refuses a draft in conflict, so Save stays inactive (`aria-disabled`, `data-state="disabled"`) after an order saved elsewhere, even after another edit, until Reload (rereads, drops the draft) or Discard. A write already in flight when the change arrives is refused by the backend (`revision_conflict`) and keeps the draft with the banner. This follows plan.md "Conflict retains user draft … until Reload is activated"; the banner text is unchanged (it never promised that Save replaces the order).
- **Focus without scroll:** a focus request that lands on the section title uses `focus({ preventScroll: true })` (`focusOptionsOf` in `editor-focus.ts`), so the bar closing on its own never scrolls the Sound page; row controls and Add keep the default scroll-into-view.
