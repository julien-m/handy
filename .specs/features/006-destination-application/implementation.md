# Implementation — 006-destination-application

Status: In Progress. The non-UI scope of the plan is implemented on `feature/006-destination-application` (Steps 0, 2, 3 with the settings UI write command, 4, and the non-UI parts of Steps 1 and 6 including the text-only history rule), behind the closed `destination-return` rollout gate (see [Rollout gate](#rollout-gate)): with the gate closed, which is the default build, dictation inserts exactly as on `dev`. The UI (Step 5 and the reason display of Step 6), the 007/009/010 adapters and every native observation beyond a read-only macOS capture are **not** done. No AC or SC is certified complete: each mapping below says what is proven by automated tests and what is missing. Read [the functional source](spec.md), [the plan](plan.md) and [the local contract](contracts/destination-contract.md); the step checkpoints are in [progress](progress.md).

## Rollout gate

Destination return is merged closed. One gate, [`DESTINATION_RETURN_WIRED`](../../../src-tauri/src/destination/rollout.rs), is the `destination-return` Cargo feature ([Cargo.toml](../../../src-tauri/Cargo.toml)), off by default (same model as 007's `smart-paste-dispatch`). `Rollout { platform_capable, wired }` decides it; both states are tested on every platform (`destination::rollout::tests`) and the full suite passes in both ([closed](proofs/claude-delivery-fix1/cargo-test-full-gate-closed.stdout), [open](proofs/claude-delivery-fix1/cargo-test-gate-open.stdout)).

- **Gate closed (default build):** `capture_at_start` and `ticket_at_stop` open no destination session, so the final text goes through `delivery::paste_as_before`, the `dev` insertion verbatim (main-thread cancellation check, settings read there, `paste-error` toast, overlay and tray reset): no useful capture, no activation, no pre-dispatch guard. `PlatformCapabilities::current()` declares no `Destination`, so `return_to_dictation_app` defaults to `false` and the settings UI command and the CLI refuse it with `validation_failed`/2, `details.reason = "unsupported_platform"` (offline and routed). Step 0 (D2–D4), the `DestinationManager`, the orchestrator, the guard and the adapters stay compiled and tested. The text-only history rule is **not** behind the gate (independent product decision).
- **Gate open:** the specified behavior on macOS and Windows (capture, return before insertion, live guard, outcome, retention; no UI yet); Linux still refuses the key.
- **Conditions to open it (both required):** (1) the native macOS proof of activation and guard, run with Julien ([procedure](progress.md#native-macos-proof-to-run-with-julien-activation-and-guard)): return to TextEdit, Notes, ChatGPT and Comet, closed destination, and an application switch during `paste_delay_ms` refused; (2) the Penflow-certified UI: badge, cross, non-activating menu, settings toggle with its unavailable reason, reason display ≥ 4 s.
- **Opening checklist:** enable `destination-return` by default in `Cargo.toml` (or remove the gate and `rollout.rs`), rerun the full suite, regenerate nothing else (no DTO or schema depends on the gate), and record the change in the changelog: the default of `return_to_dictation_app` becomes `true` on macOS and Windows for installations that never set it.

- **History rule (delivered, shared with 005):** 005 Step 7 reuses `managers/history_store.rs` and migration 5 and adds only its prompt metadata columns and its own tests.
- **Owners not delivered:** 007 smart-paste adapter behind `InsertionPort`, 009 Enter consumer (`claim_enter`), 010 `RecoveryPort` and reason bubble.
- **Native macOS (required before Implemented and before opening the gate):** activation, last window/Space, focus preservation, the guard refusing an application switch during `paste_delay_ms` (live Accessibility read), capture/activation/heartbeat timings with the real binary and TextEdit, Notes, ChatGPT, Comet; manual [procedure with Julien](progress.md#native-macos-proof-to-run-with-julien-activation-and-guard); the `scripts/destination-native-proof.ts` harness is not built. Also settle there whether activation must be requested from the main thread (macOS 14+ cooperative activation).
- **Windows and Linux (pending release evidence, D1):** (a) Windows: `bun scripts/destination-native-proof.ts --binary <absolute-windows-release-binary> --platform windows --out <proof-directory>` with two applications, multi-window, restricted activation, menu without activation, unsupported reason and CLI parity, plus hosted UWP/WinUI applications: dictation started in Calculator then switch to Settings refuses the insertion (two hosted apps are distinct AUMIDs), a minimized or suspended hosted app is unreadable, and `ApplicationFrameHost.exe` never appears in the menu — the adapter is compile-checked only ([harness](proofs/claude-impl/windows-check/src/lib.rs)); (b) Linux: the settings window shows the setting unavailable with its reason, `handy settings output set return_to_dictation_app true --json` returns `validation_failed`/2 with `details.reason = "unsupported_platform"`, and insertion behaves as today.
- **Older Handy binary after history migration 5 (pending release evidence):** migration 5 rebuilds `transcription_history` with a nullable `file_name` and sets `user_version` to 5. Check: on a profile migrated by this build, start the previous released Handy binary. Expected today: `rusqlite_migration` refuses the newer database (`DatabaseTooFarAhead`) and `HistoryManager::new(...).expect(...)` in `lib.rs` stops the startup; even without that, a text-only row (`file_name` NULL) cannot be read by the older row mapping. Same downgrade pattern as every earlier migration; making a too-new history non-fatal is a possible later change, not part of 006.
- **Double failure (documented):** a failed insertion whose history save also failed leaves the transcript only in the volatile `RecoverySlot` (lost at the next retained dictation or at exit) until 010 reads it; the toast tells the user it was not saved, without the text. No clipboard fallback (007 owns the clipboard).
