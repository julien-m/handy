## Step 3 — notes

- **Delivered:** `AppSettings.return_to_dictation_app` (serde default `PlatformCapabilities::current().supports(Destination)`, never written at startup), descriptor row (owner `output`, runtime effect `None`), `PublicSettings` field, `OUTPUT_KEYS: [&str; 11]`, `KEY_CAPABILITIES` row → `required_capability("return_to_dictation_app") == Some(Destination)`; session commands `destination_snapshot`, `destination_support`, `destination_menu`, `choose_destination`, `remove_destination` (async, registered, exported); `destination::app::install` registers `Arc<DestinationManager>`, `Arc<RecoverySlot>`, `Arc<OutcomeRegistry>` and emits `destination-support-changed` after one startup foreground read; `destination-changed` on a badge choice.
- **Deviation — settings UI command not registered:** `change_return_to_dictation_app_setting` (plan Step 3) is **not** delivered. A Tauri command returning `Result` makes tauri-specta generate one `e as any` in `src/bindings.ts`; the repository conventions baseline allows exactly the 105 existing ones (`ts.no_as_any`, count-based), so any new `Result` command fails the gate, and the baseline must not be rewritten. The setting is fully writable through the shared service (CLI offline and routed, `validate_ui` parity proven in `destination_cli.rs`); the UI write command belongs with the settings toggle (Step 5) and needs a maintainer decision first: exclude the generated `bindings.ts` from `ts.no_as_any`, or accept a baseline update. The same constraint is why the session commands return typed answers (`MenuAnswer`, `ChoiceAnswer`: `{status, value}`) instead of `Result`.
- **Bindings:** regenerated by the supported specta export (debug binary, isolated `HOME`, headless `--list-models`, which exports before running and never contacts a running Handy). The export also refreshed two stale 008 doc comments.
- **Not claimed:** no Linux execution of the refusal (the offline refusal branch of `destination_cli.rs` runs only on a build without the capability); no UI.
