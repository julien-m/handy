## Step 4 — notes

- **Flow delivered:** `actions.rs` reads the destination right after the settings, before any overlay is shown, and commits it only when `try_start_recording` succeeds (a failed start discards it); `stop` takes the dictation ticket and marks the session processing; the final text goes through `destination::delivery::insert_final_text`, which runs `insertion::Orchestrator::deliver` on a blocking worker: freeze (menu closed, later choices refused) → paste method `none` skips activation (`skipped`) → resolve the instance by identity (captured PID first, one restarted instance, ambiguous or closed fail closed) → one activation request unless already in front → foreground sampling every 20 ms on the worker until in front or 1 s elapsed (999/1000 ms accepted, 1001 ms refused, injected clock) → the existing `clipboard::paste` runs on the main thread as before with a `DispatchGuard` that it calls after `paste_delay_ms` and before the first key/text/script/reliable paste: cancellation, same PID and identity in front (else `activation_failed`, no retry, no reactivation), `DestinationContext`, the 010 verdict (`NoRecoveryConsumer` today), then disposition `Insert`. Results map through `map_method_result`; failures set `Recover`; a failed transcript is retained in `RecoverySlot`; one `InsertionOutcome` (metadata) is published to `OutcomeRegistry` and as `insertion-outcome`; `paste-error` stays the visible fallback. Cancellation (`cancel_current_operation`) and the no-insertion paths end the session.
- **History:** `save_history` reports `saved` (with entry id), `not_saved` (no WAV) or `failed` from the actual `save_entry` result; it is saved before insertion, as before.
- **Deviations / not done:** the orchestrator tests are inline unit tests (`destination/insertion_*.rs`) instead of `tests/destination_insertion.rs`, because the fakes and the manager internals are crate-private; the existing paste delays and direct typing still run on the main thread exactly as before (only the activation wait moved to a worker) — extracting them (plan Step 4 "move waits off main") is not done, so the UI-freeze risk of long existing delays is unchanged and unmeasured; no chunk-boundary check during direct typing (residual focus race documented in the plan); the guard placement inside `clipboard.rs` is proven by code review only (no unit test can drive `paste` without a Tauri app); no 007 smart-paste adapter (007 not delivered).
- **Native evidence:** none for activation, focus, timing or insertion — the real Handy binary and target applications are needed (Step 7 harness, not built). Windows: compile-only.
